# Phase 11 — Hardware-in-the-Loop Evidence Separation

## Outcome

Phase 11 is complete and was rerun on 2026-09-03 with the corrected normalized-unit firmware. The evidence is separated into three non-interchangeable layers: offline Python evaluation, independently compiled host-C++ parity, and on-target replay on a physical ESP8266EX. This separation prevents numerical parity from being misreported as live smart-meter validation.

The canonical claim is:

> A compact standardized linear forecasting computation and its residual-threshold decisions were transferred from Python to C++ and reproduced on a physical ESP8266EX for all 933 held-out feature vectors.

The canonical limitation is:

> The ESP8266 experiment replayed fixed dataset-derived vectors and did not measure household voltage, current, power, or energy; it therefore does not constitute a calibrated smart meter or a field anomaly trial.

## Evidence architecture

| Layer | Execution environment | Input | Verified result | What it does not establish |
|---|---|---|---|---|
| 1. Offline reference | Desktop Python | Chronological 933-row test set | Reference predictions, MAE/RMSE, residual flags, supplied-label confusion matrix | C++ portability or hardware behavior |
| 2. Compiled-host parity | Independent C++17 executable | Same 933 features and targets | 933/933 prediction matches within `1e-6`; 933/933 decision matches | ESP8266 execution, timing, or memory |
| 3. Physical-device replay | ESP8266EX NodeMCU 1.0 | 933 fixed vectors stored in program flash | 933/933 prediction parity; 933/933 decision parity; on-device timing | Live lag-buffer forecasting, calibrated sensing, physical-fault accuracy, or energy per inference |

The machine-readable evidence map is `outputs/phase11_hil_evidence_layers.json`, generated by `tools/run_phase11_hil_evidence_audit.py`.

## Layer 1 — Offline Python reference

The model was fitted on 2,984 chronological rows, its threshold was calibrated on the next 747 rows, and it was evaluated once on the final 933 rows. The frozen reference result was:

| Metric | Python reference |
|---|---:|
| MAE | 0.1307837086 normalized units |
| RMSE | 0.1623896726 normalized units |
| Residual threshold | 0.3830260556 normalized units |
| TP / FP / FN / TN | 8 / 0 / 44 / 881 |
| Precision / recall / F1 | 1.0000 / 0.1538 / 0.2667 |

The classification metrics compare with labels described by the dataset publisher as Isolation Forest outputs. They must be described as agreement with supplied pseudo-labels, not physical fault-detection accuracy.

## Layer 2 — Independently compiled host C++

The generated Arduino-compatible model header was compiled into a C++17 executable and tested outside the Python inference path. At an absolute tolerance of `1e-6` normalized units:

| Metric | Compiled-host result |
|---|---:|
| Prediction matches | 933 / 933 |
| Decision matches | 933 / 933 |
| Mean absolute Python/C++ difference | 0.000000017288 |
| Maximum absolute Python/C++ difference | 0.000000075572 |

This is a pre-flash export test. It verifies feature order, generated constants, threshold serialization, and `float32` arithmetic. It does not replace physical-device testing.

## Layer 3 — Physical ESP8266 replay

The v2 device record shows that a physical ESP8266EX replayed all 933 fixed held-out vectors:

| Metric | Physical-device result |
|---|---:|
| Prediction parity | 933 / 933 |
| Residual-decision parity | 933 / 933 |
| Maximum Python/device difference | 0.000000089 normalized units |
| Device MAE | 0.130783707 normalized units |
| Device RMSE | 0.162389636 normalized units |
| Full 933-vector validation-loop time | 60,122 µs |
| Mean of 30 batch-average inference times | 50.427 µs |

Thirty timing batches each executed 2,000 predictions. Their batch-average inference times ranged from 50.361 to 50.700 µs; Phase 12 reports the full distribution. These are batch averages for the arithmetic kernel, not individual-inference or end-to-end latency observations.

The physical run also recorded HTTP 200 and a ThingSpeak entry after benchmarking. That observation verifies that telemetry continued in the prototype configuration; it does not demonstrate secure communication, long-duration reliability, or end-to-end forecast latency.

## Consistency checks across layers

- Python and device confusion matrices are identical.
- Python/device MAE differs by only `1.60e-9` normalized units.
- Python/device RMSE differs by only `3.66e-8` normalized units.
- The independently compiled host result and the physical result both pass all 933 prediction and decision checks.
- Normal and full-validation firmware compile successfully after the corrected unit names were introduced.

## Paper-ready methods wording

> We trained a standardized linear forecaster using a chronological fit/calibration/test split and serialized its parameters to 32-bit C++ constants. Before deployment, an independently compiled host executable evaluated all 933 held-out vectors against the Python reference. We then stored the same fixed vectors in program flash and replayed them on a physical ESP8266EX. We compared predictions within a declared absolute tolerance and compared residual-threshold decisions exactly. The on-target experiment evaluates numerical portability and computational feasibility; it does not include a calibrated electrical sensing front end or live construction of lagged features.

## Paper-ready results wording

> The host-C++ implementation matched all 933 Python predictions within `1e-6` normalized units and reproduced all 933 residual decisions. Physical ESP8266 replay also reproduced all 933 predictions and decisions; the largest observed Python/device difference was `8.9e-8` normalized units. Across 30 batches of 2,000 predictions, mean batch-average inference time was 50.427 µs. These findings demonstrate numerical portability under held-out-vector replay, not field accuracy of a deployed smart meter.

## Claims explicitly prohibited by current evidence

- “The ESP8266 forecasted live household energy consumption.”
- “The prototype measured kWh accurately.”
- “The device detected real electrical faults with 100% precision.”
- “The complete system consumed a measured amount of energy per inference.”
- “ThingSpeak communication was secure or reliable over long-term operation.”
- “The reported timing applies to all ESP8266 boards or compiler configurations.”
